Appointment Booking System
Goal
Build a full-stack app where an Admin publishes availability slots and a Customer 
books/cancels them. The system must remain correct under real-world 
conditions (concurrency, retries, auth boundaries, time rules).

Roles
Admin

Create availability slots
View all slots and associated bookings
Cancel a slot (define behavior for booked slots; document it)

Customer
View available slots
Book a slot
Cancel their own booking
View “My bookings”

Core Requirements
Authentication & Authorization

Login required for booking and all admin actions
Role-based access enforced on the backend:

Admin-only: create/cancel slots, view all bookings
Customer-only: book/cancel own booking, view own bookings

No “security by UI hiding”—server must reject forbidden actions

Complex Areas (Must Be Handled Correctly)
1) Double Booking / Concurrency Safety (Mandatory)
Two customers can attempt booking the same slot at the same time. Only one 
must succeed.
Expected implementation includes DB-level guarantees, such as:

Transaction + row locking (SELECT … FOR UPDATE), or
Atomic update strategy (UPDATE slot SET status=BOOKED WHERE id=? AND 
status=AVAILABLE), or
Unique constraint ensuring only one active booking per slot

Conflict should return a clean response (recommended: 409 Conflict).

2) Slot Overlap Rules
Admin slot creation must prevent time overlaps. Define boundary rules clearly:

e.g. [start, end) vs [start, end] behavior
Must be enforced on backend (UI validation alone is insufficient)

3) Cancellation Semantics (State Machine)
Define valid transitions and enforce them:

Slot cannot be BOOKED without an active booking
Booking cannot remain active if slot is AVAILABLE
Avoid deleting rows; prefer status + timestamps

5) Idempotency / Retries
Handle:

double clicks on Book
request retries due to flaky networks
Return stable results (either idempotent booking or correct duplicate 
prevention).

6) “Available” Definition
Available slots listing must exclude:

past slots
cancelled slots
booked slots
Sorting and filtering must be consistent server-side.

7) Error Handling
Use proper status codes:

400 validation
401/403 auth/role
404 missing resource
409 booking conflict
Provide useful error payloads.
